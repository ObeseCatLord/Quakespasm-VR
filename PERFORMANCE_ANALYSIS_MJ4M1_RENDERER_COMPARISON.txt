QuakeSpasmVR performance analysis: mj4m1, Ironwail, and VKQuake
Date: 2026-06-06

Scope
=====

This note compares the current quakespasm-openvr fork against:

- Ironwail: /home/obesecatlord/Documents/ironwailVR/ironwail
- VKQuake: /home/obesecatlord/Documents/quakespasmvr/vkquake
- Current fork: /home/obesecatlord/Documents/quakespasmvr/quakespasm-openvr

The immediate performance problem that prompted this analysis was mjolnir map
mj4m1 running poorly in VR with frame drops. The goal is to list the renderer
and engine features that Ironwail and VKQuake use for better performance, how
those differ from this fork, and how to copy or implement them here in a way
that can be picked up later without repeating this investigation.


Executive summary
=================

mj4m1 is a worst-case map for QuakeSpasmVR's current renderer. It is BSP2, has
no visibility lump, has hundreds of thousands of faces, and has many static and
alias entities. The current fork still uses a mostly classic QuakeSpasm CPU
renderer path:

- Each rendered view runs CPU PVS/leaf/surface marking.
- Brush/world surfaces are chained and drawn through older texture/lightmap
  chains.
- Alias models are sorted a little, but still submitted one entity at a time.
- VR renders each eye through the screen/render path separately, so CPU scene
  setup and entity processing are effectively doubled.

Ironwail is faster mainly because it moved major parts of the OpenGL renderer
to GPU-driven or batched paths:

- GPU surface marking/culling using compute shaders.
- Prebuilt world/brush model GPU buffers.
- Indirect/multidraw brush rendering.
- Entity sorting by model type and model.
- True instanced alias rendering.
- Persistent/frame resource upload buffers.
- Clustered dynamic light data.

VKQuake is faster for similar reasons but through a Vulkan renderer:

- A render task graph.
- Parallel and SIMD surface marking.
- Vulkan indirect brush draws.
- GPU lightmap update compute.
- Compute pipelines for warp, interpolation, skinning, and indirect draw setup.
- Staging buffers and descriptor-managed GPU resources.

The highest-value practical improvement path for this fork is:

1. Add better renderer timing counters for VR and large maps.
2. Share VR visibility/entity setup between eyes where possible.
3. Port Ironwail-style entity sorting and alias instancing first.
4. Port Ironwail's brush/world GPU buffer and indirect draw path next.
5. Add Ironwail-style frame upload buffers.
6. Add or adapt VKQuake-style tasking only after the render state is cleanly
   separated from CPU-only prep work.

Porting VKQuake's whole Vulkan backend is much larger than the likely benefit
for this fork. Ironwail's GL renderer is the better source for code to copy
first because it shares more ancestry with QuakeSpasm and this fork.

Current fork renderer shape
===========================

Current fork already has useful compatibility work and some renderer cvars, but
it does not yet have Ironwail's GPU-driven world path or true alias instancing.


External VIS note
=================

mj4m1 has an empty VIS lump. That is a content-side performance problem.

Current fork, Ironwail, and VKQuake all have external .vis loading paths that
are gated to normal BSP29 in the inspected code:

- Current fork: Quake/gl_model.c:2361
- Ironwail: /home/obesecatlord/Documents/ironwailVR/ironwail/Quake/gl_model.c:2440
- VKQuake: /home/obesecatlord/Documents/quakespasmvr/vkquake/Quake/gl_model.c:3113

That means simply adding a .vis file for mj4m1 may not work unless this fork is
extended to accept the relevant external VIS format for BSP2, and unless a valid
VIS file for the map exists. No installed mjolnir .vis file was observed during
this analysis.

Implementation option:

1. Short term: add a clear warning/log line for BSP2 maps with empty VIS:
   "BSP2 map has no VIS; performance may be poor."
2. Medium term: investigate whether the map source can be vised and rebuilt, or
   whether the mjolnir distribution includes an external visibility file under
   a nonstandard name.
3. Engine term: extend external VIS loading to BSP2 only after confirming a
   real BSP2 external VIS format to support. Do not invent a format unless a
   toolchain will produce it.


Ironwail comparison
===================

Ironwail is the best source to copy from first because it is OpenGL based and
shares more QuakeSpasm ancestry than VKQuake.


1. GPU surface marking and culling
----------------------------------

Ironwail code:

- /home/obesecatlord/Documents/ironwailVR/ironwail/Quake/r_world.c:58
  R_MarkVisSurfaces uploads PVS and frame data to GPU, clears indirect buffers,
  and dispatches a compute shader to mark visible surfaces.

- /home/obesecatlord/Documents/ironwailVR/ironwail/Quake/r_world.c:111
  R_MarkSurfaces chooses the PVS and calls R_MarkVisSurfaces.

Current fork:

- Quake/r_world.c:95
  R_MarkSurfaces walks the BSP, marks surfaces, builds texture chains, updates
  lightmaps, and stores efrags on the CPU every view.

Why it matters:

- mj4m1 has 220,457 leaves and 543,349 marksurfaces. CPU walking this data per
  view is expensive, and VR doubles the cost.
- GPU marking avoids much of the serial CPU traversal and prepares data for
  indirect draws.

How to implement here:

1. Add a cvar such as r_gpuworld, default 0 at first.
2. Copy Ironwail's GPU surface metadata structures and compute shader support
   into this fork's GL renderer.
3. During model load, build GPU buffers for surface metadata, mark surfaces, and
   indirect draw commands.
4. In R_MarkSurfaces, keep the old CPU path as fallback. When r_gpuworld is on
   and GL 4.3/compute support exists, upload PVS/frustum/view data and dispatch
   the mark compute shader.
5. Make VR use one common GPU mark for both eyes where possible, using a
   conservative stereo frustum or union-frustum data.
6. Validate against AD, mjolnir, dwell, qbj3, and normal id1 maps.

Risks:

- Requires GL 4.3 compute/SSBO support.
- Needs careful fallback for older hardware and for VR-specific render paths.
- Must preserve dynamic lightmap and efrag behavior.

2. Use VKQuake's lightmap compute data layout as a reference.
3. In OpenGL, either port Ironwail's relevant dynamic light approach or add GL
   compute versions only after the world buffer system exists.

Phase 1: content and VIS handling
---------------------------------

Goal:

- Avoid spending engine time compensating for bad or missing visibility if a
  real visibility solution exists.

Implementation:

1. Add better warnings for BSP2 maps with empty VIS.
2. Search the mjolnir package for map sources or external VIS data.
3. If a valid BSP2 external VIS file exists or can be generated, extend the
   external VIS loader to support BSP2 safely.
4. If no VIS data exists, continue renderer optimization. Engine-side GPU
   marking/indirect draw is still needed.


Phase 2: shared VR visibility/entity setup
------------------------------------------

Goal:

- Stop duplicating expensive CPU scene setup for left and right eye.

Current problem:

- Quake/vr.c renders each eye separately through SCR_UpdateScreenContent.
- That reruns R_SetupView and R_MarkSurfaces for each eye.

Implementation:

1. Split current render setup into:
   - common frame setup
   - common visibility/entity setup
   - per-eye projection/view setup
   - per-eye draw submission
2. For VR, compute common visibility from the HMD/head center, not from each eye
   separately.
3. Use a conservative stereo frustum:
   - union of left and right frusta, or
   - center frustum inflated by IPD and near-plane margin.
4. Build texture chains and cl_visedicts once.
5. Draw each eye using the cached visible set.
6. Do not double-apply dynamic lightmap updates. Mark/update them once per
   frame, then render both eyes.
7. Keep a cvar fallback, for example vr_shared_scene_setup 1.

Risks:

- If the shared frustum is too narrow, one eye can miss near-edge surfaces.
- If it is too wide, it may draw slightly more than necessary, but that is
  usually better than CPU-scanning the map twice.
- Need to ensure stereo-correct text/HUD/VR weapon rendering remains per-eye.

Tests:

- mj4m1 in VR, standing near doorways and near geometry.
- AD/dwell/qbj3 maps with high detail.
- Water/warp/skyroom maps.
- VR text and weapon alignment.


Phase 3: entity sorting and alias instancing
--------------------------------------------

Goal:

- Reduce CPU and GL draw overhead from many alias entities.

Implementation order:

1. Port Ironwail's entity sorting:
   - gl_rmain.c R_SortEntities
   - sorted visedict array
   - model type offsets
2. Preserve special ordering for alpha entities and sprites.
3. Add Ironwail-style aliasinstance_t and alias batch flush.
4. Port shader support for per-instance data.
5. Route only world alias entities through the instanced path at first.
6. Keep VR held weapons, controller previews, weapon wheel, and viewmodels on
   the existing path.

Expected benefit:

- Major improvement on maps with many repeated alias models, misc_model usage,
  and decorative entities.
- Lower per-eye CPU cost in VR after shared visibility/entity setup.


Phase 4: Ironwail OpenGL brush/world GPU path
---------------------------------------------

Goal:

- Move the biggest mj4m1 world bottleneck away from CPU chain walking and
  per-surface draw setup.

Implementation order:

1. Port bmodel vertex/index/metadata buffer building from Ironwail r_brush.c.
2. Add GL resource lifetime handling on map load/unload.
3. Add compute-based surface marking if GL 4.3 is available.
4. Add indirect/multidraw brush rendering.
5. Keep old draw path as fallback.
6. Make VR shared setup use the GPU world mark once per frame.

Expected benefit:

- Highest likely improvement for mj4m1 because the map has no VIS and huge
  surface counts.

Risks:

- Largest code integration effort.
- Requires careful interaction with:
  - dynamic lightmaps
  - water/warp surfaces
  - skyroom rendering
  - alpha/transparent brush entities
  - brush model movement
  - CSQC draws


Phase 5: frame upload/resource buffer
-------------------------------------

Goal:

- Prevent new batching paths from introducing GL upload stalls.

Implementation:

1. Port Ironwail's GL_Upload / GL_ReserveDeviceMemory frame resource system.
2. Use it for alias instance data first.
3. Use it for brush instance data and particles next.
4. Add diagnostic counters for upload usage.


Phase 6: dynamic light and particle follow-up
---------------------------------------------

Goal:

- Improve effect-heavy modern mod scenes after the world/entity bottlenecks are
  addressed.

Implementation:

1. Re-profile AD, dwell, mjolnir, and qbj3 after phases 2-5.
2. If dynamic light/lightmap update cost is still high, port Ironwail clustered
   light data or VKQuake-inspired compute lightmap updates.
3. If particles are high, port Ironwail's particle upload batching and OIT
   transparency path.


Phase 7: VKQuake-style CPU tasking
----------------------------------

Goal:

- Parallelize CPU-only render preparation where it still exists.

Implementation:

1. Port VKQuake's tasks.c/task API or write a small compatible subset.
2. Use tasks for CPU-only work:
   - model loading
   - entity sort-key generation
   - static model culling
   - CPU visibility/culling fallback
3. Keep GL calls on the render thread.
4. Use a cvar r_tasks, default on only after stable.

This should come after or alongside a cleaner renderer split. Adding threads to
the current mutable texture-chain renderer directly is risky.


Short-term cvars and workarounds
================================

Until the renderer is improved:

- r_drawentities 0 confirms entity cost but is not playable.
- r_particles 0 can help effect-heavy scenes but changes visuals.
- r_dynamic 0 may reduce dynamic light/lightmap work but changes visuals.
- r_scale can reduce rendered resolution as a VR fallback, but does not fix CPU
  scene setup.
- r_skyroom 0 should stay off by default unless a map needs it.
- A future vr_shared_scene_setup 1 would be a high-value default once stable.
- A future r_alias_instancing 1 should default on when supported.
- A future r_gpuworld 1 should default on only after broad testing.

Bottom line
===========

For this fork, the best practical path is not to port all of VKQuake or all of
Ironwail at once. The next durable performance work should be:

1. Measure better.
2. Stop repeating expensive scene setup per VR eye.
3. Port Ironwail's entity sort and alias instancing.
4. Port Ironwail's OpenGL world/brush GPU buffer and indirect draw path.
5. Add Ironwail-style frame resource uploads.
6. Use VKQuake tasking/SIMD ideas for remaining CPU fallback paths.

Those changes directly target the mj4m1 evidence: huge no-VIS BSP2 world cost,
many entities, and VR doubling of CPU render setup.


Implementation status started on 2026-06-06
===========================================

The first safe implementation step has been added in this working tree:

- r_perfdebug
  - 0: disabled. This is the default and should have no practical runtime
    effect.
  - 1: log slow rendered views whose total render time is at least
    r_perfdebug_min_ms.
  - 2: log every rendered view.

- r_perfdebug_min_ms
  - Default: 8.
  - Used only when r_perfdebug is 1.

Logs are written with DebugLog to debug_mapchange.log, not as onscreen console
spam. The instrumentation records:

- total rendered-view time
- skyroom, setup, surface marking, warp update, scene, and scale timings
- world, water, opaque entity, alpha entity, dynamic light, particle, outline,
  viewmodel, and debug-draw timings
- PVS source counts: normal leaf PVS, fat PVS, novis
- leaf scan, visible leaf, culled leaf, marksurface, unique surface, culled
  surface, chained surface, and efrag-leaf counts
- opaque/alpha entity counts by alias, brush, and sprite type
- alias draw, alias cull, GLSL alias draw, and GLSL alias batch flush counts

Also added:

- A debug-log-only warning when a BSP2 map loads with no VIS data. This is meant
  to flag maps like mj4m1 without adding HUD/console noise.

Networking impact:

- No networking files or packet paths were changed by this instrumentation step.

VR impact:

- VR rendering behavior is unchanged. The instrumentation only records timings
  around existing calls. VR-specific rendering paths and input paths are not
  modified.
